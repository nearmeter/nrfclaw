# nRFClaw AI Knowledge Base

## Purpose
This file is a self-contained technical context for an AI assistant helping with nRFClaw. Treat source code and release-specific build output as authoritative when they conflict with prose. Never claim that generated bytecode is semantically correct merely because it compiled: requested capabilities/actions must be present in the lowered program.

## Project
nRFClaw is an AI-programmable, ultra-low-power embedded platform centered on Nordic nRF52832. Project site: https://nrfclaw.cloud/. Public publisher: NearMeter, https://github.com/nearmeter. Contact: nrfclaw@nearmeter.com.

The MCU does not run an LLM. Natural language is processed on a host by the deterministic semantic compiler and optionally an external/local AI agent. Semantic IR/schema/capability checks and deterministic lowering are the authority before bytecode is accepted.

## Runtime Model
Natural language -> semantic parser/optional agent -> Semantic IR/plan -> validation -> deterministic lowering -> compact VM bytecode -> BLE NUS upload -> VM execution.

Programs can be MANUAL or BOOT. BOOT programs are persisted and start after reset. WAIT/event operations are intended to return the system to the low-power firmware loop rather than busy-spin. P0.21 remains the physical recovery/programming path.

## BLE Planes
NUS programming plane: physical programming mode entered with P0.21; device advertises nRFClaw(NUS)-XXXXXX.
Application/NDP plane: normal HA/application interface; device advertises nRFClaw(NDP)-XXXXXX.
Application service UUID: 4e52a800-0000-10a7-d24b-6a3244619a47. RX: ...a801..., TX notify: ...a802....
The firmware arbitrates the single advertising set. VM advertiser/tracking can take ownership; P0.21 has priority and can reclaim BLE for programming.


## Home Assistant Transport Roles and NinaLink
Home Assistant transport is a persistent role, not merely a temporary radio command. The three production roles are DIRECT_BLE, NINALINK_NODE and BRIDGE.

DIRECT_BLE: Application/NDP is enabled. Passive telemetry/events use BLE advertising where possible; short NDP sessions are used for control/snapshots. This is a low-power battery-capable role.

NINALINK_NODE: Application/NDP is OFF. The node uses LLCC68 NinaLink contacts/reports through a separate bridge; default contact/report period is 20 s. Between contacts the node returns the radio/MCU to the low-power path. P0.21/NUS remains available for maintenance. Shorter report periods trade power for lower latency.

BRIDGE: Application/NDP is enabled for Home Assistant and the bridge keeps NinaLink LoRa RX active continuously. The bridge is the always-listening gateway and is therefore a higher-power role than a NinaLink Node.

NinaLink Network ID is 16-bit. `0x0000` means legacy/unprovisioned. Prompt provisioning uses `0x0001..0xFFFF`. `Enable Home Assistant in bridge mode.` reuses a persisted non-zero ID or creates one when unprovisioned. A first-time node must use the bridge ID, for example `Enable Home Assistant in LoRa mode on network 0x7A31.`. Network provisioning is a host-side `prompt --upload` action before VM bytecode is stored; raw `.bin` bytecode does not provision the Network ID.

The Network ID is isolation/admission metadata, not the Application/NDP authentication key.

## NDP Owner Key
Application/NDP protection is optional. Through the physical P0.21/NUS owner plane, `ndp-key-generate` creates/persists a 256-bit key and prints it as `hex:<64 hex digits>`. Home Assistant stores the same value in its NDP access key field. `ndp-key-get` can read it again through physical NUS. Once a key exists, Application/NDP requires it; P0.21/NUS remains the owner/recovery path.

## Hardware
Reference: NINASENSE. MCU: nRF52832. Optional/full capability hardware: LLCC68 LoRa; LIS2DH12 accelerometer; DS18B20 temperature; Hall/reed inputs; battery ADC/divider; 32.768 kHz crystal; UART pins; P0.21 programming button. Board abstraction also contains pca10040 and halfmoon profiles.

Capabilities: GPIO, BATTERY, DS18B20, ACCEL, LORA, BLE_APP, RTC, HALL, STATE, SERIAL, TRACKING, VIB_AUTO/VIB health.

## Power Rules
Design principle: sleep first, event-driven instead of polling, radios asleep unless needed. Periodic LoRa TX wakes LLCC68 for TX and returns it to sleep. BLE advertising/tracking uses short radio events separated by sleep. Continuous LoRa RX and normal continuous Serial RX are higher-consumption because receivers must remain active. Low-power Serial RX disables unrelated loads but cannot reach the pure minimum baseline while UART RX listens. Tracking/OpenHaystack is not a Higher-consumption category.

Minimum-power certified prompt: `At boot, disable everything to test minimum power consumption.` -> PROGRAM BOOT / SYSTEM MINIMUM POWER / END. P0.21 remains available.

NINASENSE current measurement: use the two current-test pins beside the U7/SW1 current-test area with an ammeter in series. Open/remove the normal current link so supply current passes through the meter. Start in mA if necessary; discharged capacitors can overload a fixed uA range. After capacitors charge, reconnect in uA range. Never place an ammeter directly across the battery like a voltmeter.

## LoRa
Radio: LLCC68. Persisted RF profile supports frequency, TX power up to platform limits, SF, BW, CR. TX is short-duty. RX listening is higher-power. CLI includes lora-get and profile modification/diagnostics. VM supports literal send, buffer send and receive-to-buffer primitives.

## Serial
Serial TX can be brief. Serial RX must listen. A low-power serial-router policy shuts down unrelated services while retaining UART RX. It reduces consumption but does not make active UART listening equal to the minimum-power baseline.

## Sensors
DS18B20: temperature. Battery: centivolt/voltage formatting path. LIS2DH12: motion, TAP, FALL, vibration. Hall/reed: event and counting. RTC: low-power schedule/wake.

## VIB_AUTO
VIB_AUTO is a local self-learning vibration monitor. Config contains learning_time_s, discovery_interval_s, normal_interval_s, suspicious_interval_s, wake threshold/duration, profile match/adaptation thresholds, candidate confirmations, alarm consecutive count, max_profiles <= 6, sensitivity, adaptation controls and arming_delay_s.

The arming/initial delay occurs before learning, allowing installation/fixation motion to settle. Discovery then samples active vibration windows and clusters recurring patterns. Profiles are persisted. Each profile stores RMS mean/tolerance, peak mean/tolerance, peak-to-peak mean/tolerance, zero-crossing mean/tolerance, observations and confidence. Profiles are unlabeled operating clusters; a washing machine may naturally create multiple profiles corresponding to recurring regimes such as wash/agitation/spin, but firmware does not assign those human names. Monitoring selects the best profile and scores deviation. Very-normal samples may slowly adapt a profile. Anomalous windows must not be learned as normal. Repeated abnormal windows can emit VIB_AUTO.ALARM.

Validated example: `At boot, activate VIB_AUTO on the machine with learning 2 hours and initial delay 1 minute; if vibration becomes abnormal, notify Home Assistant.` Lowering: BLE NDP ON; VIB_AUTO CONFIG learning=7200s initial=60s; START; loop WAIT_EVENT VIB_AUTO.ALARM; HA EVENT cap=13 op=4 value=R7.

CLI inspection: vib-auto-status, vib-auto-baseline, vib-auto-diagnostics, vib-auto-trace. Direct config supports `vib-auto-config --learning-time 2h --arming-delay 60`; `vib-auto-start --relearn` clears/restarts discovery behavior as requested.

## Tracking / OpenHaystack
Tracking uses BLE advertising and key rotation. It is low-duty advertising, not continuous RX. Validated prompt: `At boot, enable tracking every 5 seconds.` -> TRACKING CONFIG interval=5000ms; rotation default 10800s; TRACKING START.

Provisioning workflow: enter NUS with P0.21, upload BOOT tracking program, reset so BOOT initializes tracking, then press P0.21 again and run `tracking-provision --name ...` to display provisioning QR/URL. CLI also supports tracking-info, tracking-identity, tracking-export, tracking-enable and tracking-stop.

## Home Assistant / Telegram
Home Assistant uses Application/NDP BLE. `python3 nrfclaw_cli.py ha scan` lists visible peripherals; device-info/sensors/status inspect a selected device. Telegram is normally integrated through Home Assistant/gateway, not directly on nRF52832. Example: user asks Telegram `What is the current temperature?`; HA answers from latest sensor entity. Motion/VIB_AUTO/FALL events can trigger Telegram notifications through HA automation.

## BLE Beacon Semantics
Static name and dynamic advertising data are different. `BLE NAME "X"` configures a name. `BLE ADV BUFFER` publishes the current VM buffer in advertising data and does not necessarily rename the scanner-visible device. Dynamic sensor beacon programs should be inspected by advertising payload, not only device name.

## Bootloader / DFU
Compact BLE DFU bootloader. Current linker flash region: 0x0007A000..0x0007EFFF (20 KiB reserved); metadata page 0x0007F000. Do not confuse reserved region with actual used flash. Exact Flash/RAM usage must be generated from the public release build. Bootloader intentionally excludes application VM/sensors/LoRa/semantic compiler and uses conservative BLE transfer/CRC validation for reliability, including macOS/CoreBluetooth compatibility.

## CLI
Install Python venv and requirements. `ha scan` discovers devices. Press P0.21 for NUS before programming. `prompt --standalone` forces deterministic offline compilation. `prompt --agent` forces configured agent. `--boot` forces BOOT persistence. `--upload` writes bytecode to the board. `--run` starts uploaded MANUAL programs; BOOT programs start after reset.

Validated composite example: `Read temperature and battery, format both values in one message, and send it over LoRa every 10 minutes, repeating continuously.` -> TEMP read R0; BAT read R1; format `T=... ,B=...`; LoRa buffer send; WAIT 600s; loop.

## Agents
Supported configured providers in CLI: openrouter, gemini, ollama. API keys are referenced through environment variables and must never be committed. Agent output is not trusted bytecode. The host validates Semantic IR/capabilities and performs deterministic lowering. Unsupported semantics must be rejected rather than silently dropping clauses.

## Canonical Machine/Event Semantics
English is the canonical standalone normalization language. These meanings are authoritative:
- `machine starts running` -> `VIB_AUTO.MACHINE_ON`, HA app operation 1.
- `machine stops running` -> `VIB_AUTO.MACHINE_OFF`, HA app operation 5.
- `vibration becomes unusual/strange` -> `VIB_AUTO.WARNING`, HA app operation 3.
- `vibration becomes abnormal/anomalous` -> `VIB_AUTO.ALARM`, HA app operation 4.
- `via Telegram through HA` is HA-side delivery intent; firmware emits the HA event and does not implement Telegram itself.
- `Every HALL1 pulse represents 1 liter. Accumulate the total consumption and display it in Home Assistant.` uses the dedicated Hall semantic-volume compiler family, persistent compiler-owned state[15], and retained semantic VOLUME publication.

The dedicated production families `ha-transport-*`, `hall-semantic-volume*`, and `vib-auto-machine-ha-event` are resolved by the authoritative deterministic compiler before an external semantic agent is invoked. This prevents Semantic IR v1 from approximating persistent transport-role or host-provisioning behavior that it cannot represent exactly. External agents still receive the same knowledge base for interpretation/QA, but they never emit trusted VM bytecode.

## Semantic Safety Rule
For composite prompts, success requires semantic coverage, not just a compiler exit code. If a prompt requests FALL + temperature + battery + LoRa + BLE, the lowered program must contain the FALL wait, both sensor reads, formatting, LoRa send and BLE advertise operations. `semantic_certified=true` alone is not sufficient if the certifier does not check every requested clause.

## Build
Expected public vendor subset: vendor/nrf5sdk. Build firmware with `make configure BOARD=ninasense NRF5SDK=vendor/nrf5sdk`, then `make`. Bootloader: `make bootloader BOARD=ninasense`. First SWD install: erase, flash SoftDevice, install bootloader, flash application, reset. Preserve third-party Nordic licenses/notices.

## Release Discipline
Do not publish Studio source in the first public release. Do not publish keys, .env, caches, test results or development artifacts. Before a release, build firmware and bootloader from the vendored subset, report exact size output, validate all README prompts, and run semantic/CLI release gates. Keep main releasable and use PRs/branches for changes.
